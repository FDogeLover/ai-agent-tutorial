## 1.2 维度怎么读

| 维度 | 看什么 | 为什么重要 |
|---|---|---|
| 交付成果 | 6 份文件是否完整、准确、可编辑 | 决定任务能否一次完成 |
| 预览体验 | 产物列表、渲染、打开入口是否清楚 | 决定你是否「看得见」成果 |
| 变更核对 | 变更列表、diff、删除是否醒目 | 决定你是否「信得过」它改了什么 |
| 过程可控 | 权限文案、人工介入、接管是否清楚 | 决定风险是否在你掌控中 |
| 安全边界 | 是否遵守读取/写入边界、自检是否诚实 | 决定你的资料安全 |
| 恢复能力 | 出错/中断后有无明确恢复路径 | 决定失败成本 |

效率与成本是信息维度，不折算成分数：**Credits、积分、人民币、API 账单不是同一单位，不按数值横比**。

## 1.4 关键差异点（实测中发现，比分数更值得看）

| 现象 | 涉及产品 | 对选型的影响 |
|---|---|---|
| 无权限弹窗却读取 input 之外文件、自检未发现 | Qoder、QoderWork（Hermes 亦读取越界但自检如实披露） | 「0 弹窗」≠「合规」；对数据边界敏感者优先排除或加强人工核验 |
| 自检失真：待办未勾选却称全部通过 | Qoder | 不能把 Agent 自检当验收，教程会示范独立核验 |
| 变更统计与产物数量不一致（产物 6 份 vs 变更 5 份） | WorkBuddy | 交付清单与变更视图是两套口径，核对时都要看 |
| 审阅环节无截图证据 | TraeWork、QoderWork | 变更能力范围「未验证」，需要该能力者先自行确认 |
| 真实自动恢复案例（误写→迁移→哈希复核） | Hermes | 恢复能力唯一实证；但过程仍违反边界，「最终正确≠过程合规」 |
| 客户端成本不可见 | Codex、ZCode、Hermes | 需要自行查账单；与展示成本的产品不能直接比费用 |
| 账号受限导致整条链路不可用 | Claude | 选型第一步应是账号/地区/支付可用性检查 |

## 1.5 阅读顺序建议

1. **先看 1.3**：确认每款的测试条件，避免把 BYOK 结果当成托管结果；
2. **再看 1.4**：找出你无法接受的差异点（比如「绝不能越权读取」），先排除；
3. **最后看 1.1 与 1.2**：在剩下候选中比较六个维度；
4. 时间、成本、账号与地区信息**会过时**，核对日期见 `docs/07`（2026-08-11），正式下单前重新核对官方页面。

## 1.6 为什么不排名

- 四种成本单位（Credits/积分/人民币/API）无法折算成同一把尺子；
- 托管与 BYOK 是两种商业模式，ZCode/Hermes 的速度与质量包含模型供应商的贡献；
- 本轮只测了「材料整理」一种任务，代码优先型产品的优势场景（代码理解、diff、验证、Git）尚未统一测试——任何「第一名」都建立在不完整的任务集上；
- Claude 无性能数据，任何包含它的排名都会把猜测当事实。

因此本表只回答「**在什么条件下，哪几款值得先试用**」，不回答「谁最好」。
