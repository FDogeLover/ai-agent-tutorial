## 本章解决什么问题

「一个 Agent 不够，那就上十个」——这是最常见的系统化误区。多 Agent 不是人数优势，而是**分工优势**：只有任务真的能拆、角色真的需要分开、信息传递真的可控时，多 Agent 才划算。本章给你判断标准与四种协作模式，并带你做一次**双 Agent 协作实验**，验证「何时该多、何时该回单」。

## 从一个真实场景开始

有人搭了「专家团队」：10 个 Agent 各扮一个角色，一起写一份报告。结果：Agent A 的结论和 Agent B 互相矛盾，Agent C 引用了 A 的错误数据，整份报告返工三遍——比单 Agent 还慢。

**反例**：本书实测里，Codex 的审阅视图支持「Agent 起草 → 人审阅 → 提交」的人机协作链路，单 Agent + 人工检查就完成了全部交付，从未动用多 Agent。

**关键判断：多 Agent 解决的是「任务结构问题」，不是「模型能力问题」。** 任务拆不开、角色边界不清楚，上再多 Agent 只是把错误复制多份。

## 先说结论

1. **适合拆分的任务**：有明显子任务边界、各子任务材料相对独立、子任务结果可以拼接（如：并行调研三个话题 → 汇总）；
2. **不适合的任务**：高度耦合、需要全局一致、结果互相依赖（如：写一篇前后呼应的长文）——单 Agent 或人工分段更合适；
3. **四个协议必须定**：角色（谁做什么）、边界（谁不能碰什么）、共享上下文（大家共同看什么）、交付协议（产出物格式与交接点）；
4. **四种模式**：并行（同时干）、串行（接力干）、评审（一个写一个挑刺）、仲裁（两个方案选一或冲突裁决）；
5. **回到单 Agent 的信号**：成本膨胀、上下文互相污染、协调开销超过收益——**多 Agent 是手段，不是目的**。

## 必要概念

- **角色（Role）**：每个 Agent 的职责定义（如「研究员」「写作者」「审阅者」）——岗位说明书。
- **交付协议（Handoff protocol）**：Agent 之间传递产物的格式与规则（文件放哪、命名、交接点）——交接班记录表。
- **共享上下文（Shared context）**：所有 Agent 共同依赖的材料与规则（放固定位置，大家引用）。
- **上下文污染放大**：多 Agent 下，一个 Agent 的错误输出成为另一个 Agent 的输入——**错误会被复制和放大**（第 14 章杠杆 × 多人）。

## 四种协作模式

| 模式 | 怎么运作 | 适合 | 风险 |
|---|---|---|---|
| **并行** | 各自独立任务，最后汇总 | 子任务互相独立 | 口径不统一，汇总难 |
| **串行** | A 产出 → B 基于 A 继续 | 流水线式流程 | 前序错误传导 |
| **评审** | 一个做，一个查 | 需要质量把关 | 审阅者被带偏 |
| **仲裁** | 两个方案，人/规则裁决 | 关键决策 | 裁决成本 |

## 跟着做：一次双 Agent 协作实验

### 第一步：选一个「真能拆」的任务

例如拆成「材料调研（Agent 1）+ 报告撰写（Agent 2）」，材料调研的产出是撰写 Agent 的唯一输入。**不要**选一篇必须整体连贯的抒情长文。

### 第二步：定四个协议

- 角色：Agent 1 = 研究员（输出事实清单），Agent 2 = 写作者（基于清单写报告）；
- 边界：Agent 1 只读材料目录，Agent 2 只读 Agent 1 的产出 + 模板；
- 共享上下文：任务卡 + CONTEXT.md（放在固定路径，双方引用）；
- 交付协议：Agent 1 输出 `facts.md`（格式固定：事实/来源/置信度），Agent 2 必须基于它撰写，不得自行扩展材料。

### 第三步：串行执行并记录

Agent 1 完成 → 人检查 `facts.md`（**这是关键检查点**：确保错误不传导）→ Agent 2 撰写 → 人验收（第 10 章清单）。

### 第四步：对比单 Agent

用同样任务跑一次单 Agent（一次任务卡到底）。比较：总用时、人工介入、结果质量、成本。记录下「多 Agent 值不值」。

## 一个完整示例

- 任务：整理 10 篇材料 → 输出对比报告（子任务可拆：材料要点抽取 + 报告撰写）；
- 单 Agent：一个任务卡，边读边写，10 分钟完成，一次通过；
- 双 Agent：研究员输出 30 条事实 → 人检查发现 2 条来源可疑（阻断传导）→ 写作者成稿 → 总用时 15 分钟 + 1 次人工检查；
- 结论：本例中**单 Agent 更划算**——子任务虽可拆，但单 Agent 的上下文足够，多拆反而增加交接成本。**如果材料量 ×5、需要多人同时并行调研，双 Agent 才显优势。**

## 常见错误与恢复方法

| 现象 | 可能原因 | 怎样修正 |
|---|---|---|
| 多 Agent 产出互相矛盾 | 口径没统一 | 共享上下文写清口径，加「仲裁」层 |
| 错误被多个 Agent 复制 | 前序输出没检查 | 每个交接点设人工检查 |
| 成本翻倍效果持平 | 任务不需要拆分 | 回到单 Agent，别为「系统感」买单 |
| Agent 之间互相等 | 串行依赖设计差 | 改为并行或合并 |
| 不知道谁该对什么负责 | 角色边界不清 | 交付协议写清角色与交接物 |

## 安全提醒

- 多 Agent 的权限边界要**分别**设置，不要「一个授权全队共享」；
- 交接物（facts.md 等）可能包含敏感信息，注意脱敏；
- 仲裁场景下，最终裁决权留在人——机器之间的「讨论」不能替你承担责任。

## 本章小结

1. 多 Agent 解决任务结构问题，不解决模型能力问题；
2. 适合拆分的任务：子任务独立、材料可分、结果可拼；
3. 四个协议：角色、边界、共享上下文、交付协议；
4. 四种模式：并行、串行、评审、仲裁；
5. 错误会跨 Agent 放大，交接点必须人工检查；多 Agent 是手段不是目的。
