## 本章解决什么问题

第 15 章让你看见了 Harness 的样子，本章给你一套**可以照着搭的结构**：六层架构。每一层做什么、放什么组件、怎么和相邻层协作，一次讲清。产出：**最小 Harness 设计表**——你可以直接照着它搭一个能跑的最小版本，以后再逐步演进。

## 从一个真实场景开始

本书项目从「几个 Markdown 文件」长成了「20 多个章节 + 30 多个素材文件 + 七款产品数据」的复杂工程。能撑住，不是靠某一个模型，而是靠一层层「制度」：

- 想写新章节？→ 有章节模板和编辑规范（入口层）；
- 写之前要知道背景？→ 有 `docs/00-06` 定位与规范（上下文层）；
- 谁来写、怎么验收？→ 有写作流程与内容清单（执行+验证层）；
- 价格、版本会变？→ 有 `docs/07` 集中维护（反馈/易变信息层）。

**这套结构不是一次设计出来的，是随着「踩坑 → 补层」长出来的。** 本章给你的是它的通用骨架。

## 先说结论

1. **六层架构**：入口 → 上下文 → 执行 → 安全 → 验证 → 反馈。每层解决一类问题，缺一层就会出现对应症状；
2. **分层原则**：每层只做一件事，层间通过文件/接口传信息，不互相塞内容；
3. **演进而不是一步到位**：先搭「入口 + 上下文 + 执行」跑通最小闭环，再逐步加安全、验证、反馈；
4. **可演进的关键**：每层组件都是「文件/配置」，改一层不动其他层；
5. **最小版本就够用**：一个人的 Harness 不需要企业级复杂度，能闭环、能查、能改即可。

## 必要概念

- **分层架构（Layered architecture）**：把系统按职责分成若干层，每层只依赖相邻层。白话解释：公司分部门，市场部不直接管财务，但信息能通过流程传递。
- **入口层（Entry）**：接收任务意图的地方：任务卡、会话、定时触发。
- **执行层（Execution）**：Agent 实际干活的地方：模型 + 工具 + Skill。
- **安全层（Security）**：权限、隔离、审批、撤销。
- **验证层（Verification）**：测试、审查、验收。
- **反馈层（Feedback）**：日志、复盘、知识沉淀。

## 六层架构设计表（最小版）

| 层 | 职责 | 最小组件 | 缺了会怎样 |
|---|---|---|---|
| **入口层** | 收任务、定意图 | 任务卡模板、任务队列 | 任务描述不清，第一步就歪 |
| **上下文层** | 提供视野 | CONTEXT.md、材料清单、规则文件 | Agent 猜、误判、编造 |
| **执行层** | 干活 | Agent 产品、Skill、脚本 | 无法落地 |
| **安全层** | 控边界 | 权限卡、审批规则、备份 | 越权、误删、泄漏 |
| **验证层** | 保证质量 | 验收清单、自检要求、哈希校验 | 错误被当成正确 |
| **反馈层** | 沉淀改进 | 复盘记录、易变信息表、模板迭代 | 同样的问题反复犯 |

## 跟着做：用设计表搭你的最小 Harness

### 第一步：从「执行层」开始确认

你已有 Agent 产品（第 6 章）和 Skill（第 13 章）→ 执行层就绪。

### 第二步：补齐「入口 + 上下文」

- 入口：把你的任务卡模板放在固定位置（如 `tasks/` 目录）；
- 上下文：建立 CONTEXT.md（第 11 章已建过，确认存在）。

### 第三步：加「安全层」最简版

- 权限卡（第 8 章）放项目根目录；
- 加一条硬规则：「没有人工确认，不执行删除/发送/发布」（第 14 章全局安全底线）。

### 第四步：加「验证层」最简版

- 验收清单（第 10 章）放项目根目录；
- 每个任务卡末尾必须写「验收标准」（第 7 章已有）。

### 第五步：加「反馈层」最简版

- 每次任务后在 `reviews/` 记一条复盘（三行：做得好/问题/下次改什么）；
- 易变信息（价格、版本）集中到一张表并标核验日期。

### 第六步：画你的设计表

把上面的组件填进「六层架构设计表」，标出哪层已就绪、哪层还是空的。

## 一个完整示例（本书项目的六层落地）

| 层 | 本书项目对应 |
|---|---|
| 入口 | `templates/chapter-template.md`、内容清单 `docs/04` |
| 上下文 | `docs/00-06`（定位/目录/规范）、材料在 `research/`、`chapters/` |
| 执行 | 桌面 Agent（第 6 章选型）+ 界面讲解/产品页写作流程 |
| 安全 | 截图脱敏规则、价格核验规则、Claude 封号只写个案（`docs/03`） |
| 验证 | 章节模板的「常见错误/练习/成果」结构、链接校验、内容清单打勾 |
| 反馈 | `docs/04` 迭代、`research/` 各 run-record、`docs/07` 易变信息表 |

**关键点：这套架构的每个组件都是普通 Markdown 文件**——任何一层都可以独立修改、替换、升级，不影响其他层。这就是「可演进」。

## 常见错误与恢复方法

| 现象 | 可能原因 | 怎样修正 |
|---|---|---|
| 一开始就想搭完整版 | 违背「最小可用」 | 先六层各一件最小组件，跑通再升级 |
| 层与层互相塞内容 | 违背分层原则 | 文件只放本层职责内容，层间靠引用 |
| 只有入口+执行，老翻车 | 缺验证/安全 | 优先补验证层（错误最贵） |
| 组件散落各处找不到 | 没有目录约定 | 固定目录结构（docs/、tasks/、reviews/） |
| 架构文档写得很美但没人用 | 组件没接入流程 | 把「用架构」写进任务卡模板，强制引用 |

## 安全提醒

- 安全层组件（权限卡、审批规则）一旦定义，**不要在任务中随意绕过**——绕过一次，杠杆反向放大；
- 反馈层里记录的复盘、易变信息，注意脱敏后再存；
- Harness 组件是文件，也是「制度」：确保它们与你的组织政策一致。
