# 第 11 章：管理上下文

## 本章解决什么问题

你开始稳定使用 Agent 了，但发现它「时灵时不灵」：有时像没读过你给的材料，有时答非所问，有时把旧信息当新信息。**大多数「AI 变笨了」的真相是上下文管理出了问题。** 本章讲清 Agent 的「眼前」是怎么回事，并给你一份**项目上下文清单**，让长任务不丢、不混、不糊。

## 从一个真实场景开始

第 5 章实测里，所有产品都只拿到一份裁剪过的材料包。有趣的现象发生了：

- 多款产品的产物里出现「共同任务尚未执行」「所有产品均无记录」这类**过时结论**——因为材料包里没包含「测试已经完成」的信息，Agent 把「材料里没有」当成了「事实就是如此」；
- 一款产品的信息缺口文件里，把「材料裁剪导致缺失」当成了「项目真的缺这些内容」（TraeWork 页）。

**这不是模型笨，是上下文不完整**：Agent 只能基于你给它的上下文推理，上下文里没有的信息，它要么猜、要么误判、要么编。

## 先说结论

1. **上下文 = Agent 本次任务的「全部视野」**：你的话、它读的文件、规则、历史。没放进视野的，对它等于不存在；
2. **三类上下文问题**：不足（信息太少→猜）、过载（信息太多→糊）、污染（错误信息→带偏）；
3. **材料、规则、历史要分开给**：材料是「用什么做」，规则是「怎么做」，历史是「之前到什么程度」——混在一起会互相干扰；
4. **长任务分阶段保存状态**：不要一次塞进所有历史，用「状态文件」记录进度，分阶段交给它；
5. **第 7 章任务卡的「上下文」字段，在这里系统化**：清单化、文件化，而不是每次重打。

## 必要概念

- **上下文窗口（Context Window）**：模型单次能处理的输入总量（有上限）。白话解释：它一次能「摊在桌面上」的材料是有限的。
- **上下文不足（Under-context）**：关键信息缺失，Agent 只能靠猜 → 结果不可靠。
- **上下文过载（Over-context）**：塞了太多无关信息，淹没了关键点 → 答非所问、抓不住重点。
- **上下文污染（Context pollution）**：错误或过时信息混入 → 被带偏，且越信越错。
- **状态文件（State file）**：记录任务进度的文件（已完成/待办/决策/风险）。白话解释：任务的中途存档。

## 项目上下文清单

在任务卡基础上，为长期项目维护一份清单（放项目根目录，如 `CONTEXT.md`）：

| 模块 | 内容 | 什么时候更新 |
|---|---|---|
| 项目一句话 | 做什么、当前阶段 | 阶段切换时 |
| 关键事实 | 已确认的事实与来源（带日期） | 事实变化时 |
| 决策记录 | 做过什么决定、为什么 | 每次决策后 |
| 状态 | 当前进度：已完成/进行中/待办 | 每次任务后 |
| 规则与约定 | 命名、口径、边界（引用第 14 章） | 规则变更时 |
| 历史摘要 | 已完成任务的要点（不是全文） | 每次任务后追加摘要 |
| 易变信息表 | 价格、福利、版本及核验日期 | 定期核验（`docs/07` 就是范例） |

## 跟着做：建立并维护项目上下文

### 第一步：建 `CONTEXT.md`

按上面清单建文件，先填「项目一句话 + 关键事实 + 状态」。

### 第二步：任务开始时「喂上下文」

每次发任务，在任务卡里写清楚：**本次要用哪些材料（路径）、遵守哪些规则（引用 CONTEXT.md 相应节）、上次进度到哪（引用状态）**。不要贴全文，贴「入口 + 摘要」。

### 第三步：防污染三查

- **查过时**：材料里有没有「测试前状态」？用之前核对日期；
- **查冲突**：新材料与已有事实冲突时，以哪个为准、记录在哪；
- **查残留**：对话里有没有上一次任务的残留指令？（新任务开新会话/新任务，别续旧对话）

### 第四步：长任务分段存档

> 阶段 1 完成 → 写状态文件（产出清单 + 决策 + 遗留问题）→ 阶段 2 任务卡引用状态文件继续 → 依此类推。

分段存档的好处：即使上下文窗口有限，每个阶段只带「摘要 + 本阶段材料」，既不过载也不丢。

## 一个完整示例

本书项目就是活例子：

- 根目录维护 `docs/` 系列（项目简报、目录、编辑规范、内容清单）——每份文档只负责一个主题（第 5 篇网站化约定的实践）；
- `research/runs/*/run-record.md` 是每个实测任务的状态文件：计时、介入、问题、结论，一次任务一存档；
- `research/benchmark-summary-2026-08-12.md` 是七次任务的历史摘要——写第 5、6 章时不用重读七份记录，读摘要即可；
- `docs/07` 是易变信息表（价格核验日期），产品页引用它而不是把价格写死在正文。

**结果**：跨几十个文件的长期项目，任何一次写作任务只需引用「摘要 + 材料 + 规则」，上下文既不过载也不污染。

## 常见错误与恢复方法

| 现象 | 可能原因 | 怎样修正 |
|---|---|---|
| Agent 不知道刚做过的事 | 新会话没带状态 | 任务卡里引用状态文件摘要 |
| 回答里混入旧版本信息 | 上下文污染 | 核对材料日期，更新 CONTEXT.md |
| 塞了 50 个文件它抓不住重点 | 上下文过载 | 只给本次相关材料 + 摘要 |
| 把「材料里没有」当成「事实不存在」 | 上下文不足 | 任务卡写明「输入范围外视为未提供，不要推断」 |
| 越聊越乱 | 残留指令污染 | 新任务开新会话/新任务 |

## 安全提醒

- CONTEXT.md 里不要存密码、Token、身份证号等敏感信息——它会被 Agent 反复读取；
- 状态文件更新前确认信息仍有效，避免把过时状态再喂回去。

## 本章练习

30 分钟：为你的长期项目（或序章任务所在目录）创建 `CONTEXT.md`，完成「项目一句话 + 关键事实 + 状态 + 易变信息表」四个模块，并在下一次任务中实际引用它。

## 你应该带走的成果

- **项目上下文清单（CONTEXT.md）**：关键事实、决策记录、状态、规则、历史摘要、易变信息表。

## 本章小结

1. 上下文是 Agent 的全部视野，没放进去的等于不存在；
2. 三类问题：不足、过载、污染，各有对策；
3. 材料、规则、历史分开给，混用会互相干扰；
4. 长任务用状态文件分段存档；
5. CONTEXT.md 是长期项目的第一件基础设施。
