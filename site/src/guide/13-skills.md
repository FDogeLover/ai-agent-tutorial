# 第 13 章：从模板进阶到 Skill

## 本章解决什么问题

模板只是「文本」，Agent 每次都要重新理解，不能带参考材料、不能带脚本、不能被产品识别为「一个能力」。**Skill（技能）是模板的下一级**：把指令、参考资料、脚本打包成可命名、可调用、可分享的能力单元。本章产出**第一个最小可用 Skill**。

## 从一个真实场景开始

我反复做同一件事：把截图交给 AI 描述成结构化文字（第 5 章分析 18 张产品截图时），每次都要重写「请用 JSON 结构描述图片」的指令。写了十几遍后，我把指令 + 调用脚本 + 输出模板打包成「图像描述」Skill——从此一句话「描述这张图」即可，输出结构永远一致。

**模板省的是「打字」，Skill 省的是「理解」**：指令、脚本、参考资料一次打包，执行路径稳定。

## 先说结论

1. **Skill 是什么**：可复用能力包 = 指令（怎么做）+ 参考资料（用什么知识）+ 脚本（可选，自动化动作）+ 资源（模板/示例）；
2. **与三者的区别**：提示词是一次性口语；项目规则是常驻约束；脚本是纯代码；**Skill 是「结构化打包 + 可调用 + 可分享」的能力单元**；
3. **该建**：同一任务重复 ≥3 次、每次都要大量重复解释、且结构稳定；
4. **不该建**：做一次就完、结构天天变、或模板就能解决——复杂度不值得；
5. **最小可用原则**：从「指令 + 一个模板」开始，能跑通就算成功，脚本和资源后面再加。

## 必要概念

- **Skill（技能）**：产品能识别和调用的可复用能力包——相当于给 Agent 装一个「会做 X 事的插件」。
- **指令（Instruction）**：技能的核心文本，告诉 Agent 步骤、规则、输出格式。
- **参考资料（Reference）**：技能运行时要用的知识、示例、标准。
- **脚本（Script）**：技能触发的自动化代码（可选，如批量处理、调用工具）。
- **Slash 命令**：不少产品用 `/技能名` 快速调用 Skill（第 5 章 WorkBuddy 页有记录）。

## 一个真实 Skill 的拆解（作者的「图像描述」Skill）

> 背景：截图转结构化文字，指令长且固定、要带输出 JSON 模板、要调用视觉模型脚本——打包后一次配置，处处可用。

拆解四件套：

| 组件 | 内容 | 作用 |
|---|---|---|
| 指令 | 「用 JSON 结构描述图片：布局、区域、文字、不确定项标 uncertain；禁止编造」 | 定义怎么做、输出什么 |
| 参考 | 输出 JSON 模板示例 | 固定输出结构 |
| 脚本 | 调用视觉模型的 `describe_image.py` | 自动化「看图」动作 |
| 资源 | 无（后续可加示例库） | — |

实际效果：18 张截图批量分析，输出结构一致、可注入写作流程（第 5 章素材来源）。**注意：本教程仅是方法示范，该 Skill 的具体内容属作者个人资产，此处不展开密钥与实现细节。**

## 跟着做：创建你的第一个最小 Skill

### 第一步：选一个「重复 ≥3 次」的任务

从第 12 章模板库里挑一个（如「输出格式模板」对应的任务）。

### 第二步：写指令（核心，约 5–10 行）

用命令式写：**角色 → 步骤 → 规则 → 输出格式**。示例：

```text
你是【输出格式助手】。
步骤：
1. 读取输入材料；
2. 按模板结构组织；
3. 输出前自检：是否覆盖全部材料、格式是否符合模板。
规则：不虚构数据；来源无法确认时标注「未验证」。
输出格式：遵循【模板文件】。
```

### 第三步：打包（按你的产品方式）

不同产品对 Skill 的存放位置/格式不同（第 5 章各产品页有入口记录：WorkBuddy 的「技能与指令」、Hermes 的「技能与工具」等）。把「指令 + 模板」保存为技能文件，命名清晰（如 `weekly-report`）。

### 第四步：调用并验证

用 `/weekly-report` 或「用 weekly-report 技能……」调用一次，对照验收清单检查，迭代 v1.1。

## 一个完整示例（最小 Skill 的完整流程）

1. **问题**：每周生成「项目周报」；
2. **提示词不够的原因**：格式口径每次重写、易不一致；
3. **Skill 设计**：指令（读 CONTEXT.md 状态 + 按模板生成）+ 参考（周报模板）；
4. **一次执行**：`/weekly-report 本周完成：A、B；下周：C` → 输出固定格式周报；
5. **已知限制**：需要 CONTEXT.md 存在；口径变化时更新模板；
6. **后续改进**：接入「自动收集 Git 提交」脚本（升级为带脚本的完整版）。

## 常见错误与恢复方法

| 现象 | 可能原因 | 怎样修正 |
|---|---|---|
| Skill 建了一堆，几乎没用 | 为建而建 | 回到「重复 ≥3 次」标准，删低频的 |
| Skill 和提示词没区别 | 只有指令没打包参考/脚本 | 把模板、示例、脚本都收进技能包 |
| 不同产品里 Skill 不通 | 格式/位置不同 | 学产品规范；先做「文本版」通用技能 |
| 技能行为不稳定 | 指令模糊 | 步骤化 + 自检要求写清楚 |
| 一次都没验证就分享 | 没走验收 | 先用真实任务验证再分享 |

## 安全提醒

- Skill 里**不要**写死 API Key、账号、密码——用变量占位或环境配置；
- 带脚本的 Skill 先审查脚本内容（它会在 Agent 环境里执行），不运行不明来源的脚本；
- 分享 Skill 前检查：有没有夹带个人信息、内部路径、公司机密。

## 本章小结

1. Skill = 指令 + 参考资料 + 脚本 + 资源，是一个能力单元；
2. 重复 ≥3 次才建，最小可用起步；
3. 与提示词/规则/脚本的区别：打包、可调用、可分享；
4. 四件套里，指令是核心，脚本是加分项；
5. Skill 是个人工具箱的核心资产，也是 Harness（第五篇）的能力组件。
