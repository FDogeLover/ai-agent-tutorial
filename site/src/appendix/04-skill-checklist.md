# 附录 E：Skill 设计检查表

## 一、建之前：该不该建？（对应第 13 章）

- [ ] 同一类任务已重复 ≥3 次？
- [ ] 每次都要大量重复解释（指令长且固定）？
- [ ] 任务结构稳定（不会每周大变）？
- [ ] 普通模板（第 12 章）已经不够用？（需要带脚本/参考资料/跨任务调用）
- [ ] 我能花 30–60 分钟做最小版并验证？

全部 ✅ 才建；任一 ❌，先回去用模板或提示词。

## 二、四件套检查（建的时候）

| 组件 | 检查项 |
|---|---|
| 指令 | [ ] 步骤化（角色 → 步骤 → 规则 → 输出格式）<br>[ ] 有自检要求（输出前检查什么）<br>[ ] 有「禁止事项」（不编造、不越界） |
| 参考资料 | [ ] 模板/示例已收进技能包<br>[ ] 适用范围已写明（适用/不适用） |
| 脚本（可选） | [ ] 脚本内容已审查（会在 Agent 环境执行）<br>[ ] 无硬编码密钥/绝对路径 |
| 资源 | [ ] 需要的文件已打包<br>[ ] 命名清晰（如 weekly-report） |

## 三、调用验证（发布前）

- [ ] 用真实任务调用一次，走通「输入 → 输出」；
- [ ] 输出结构符合预期（模板生效）；
- [ ] 连续调用 2–3 次，行为稳定；
- [ ] 记录 v1.0 版本与「本次改动」；
- [ ] 失败路径：输入异常时 Skill 会不会报错或编造？有没有兜底说明？

## 四、安全审查（分享/发布前）

- [ ] 无 API Key、Token、账号、密码（用变量或环境配置）；
- [ ] 无个人信息、内部路径、公司机密；
- [ ] 无不明来源脚本；
- [ ] 无诱导越权的内容（如「绕过权限」「自动发送」）；
- [ ] 已脱敏示例数据。

## 五、迭代维护

- [ ] 每次使用后记录「不适用/没说清」的点；
- [ ] 版本号 +1 并写改动（v1.1：修改了…）；
- [ ] 三个月没用的 Skill：评估是删除还是升级；
- [ ] 规则/口径变化时同步更新 Skill 内引用（与第 14 章记忆淘汰联动）。

## 最小可用提醒

第一个 Skill 从「指令 + 一个模板」开始就够；脚本和资源是加分项，不是必需。**能跑通、能验证、能迭代，就是合格的最小 Skill。**
