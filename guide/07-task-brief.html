第 7 章：从「帮我做一下」到清晰任务卡 ​

本章解决什么问题 ​

「帮我做一下」是 Agent 使用中最常见的失败句式——信息太少，Agent 只能猜，猜错了返工，返工还怪 AI。本章教你把它升级成一张任务卡：六个字段，一次写清，让 Agent 第一次就做对。这是全教程最重要的一章，后面所有章节（权限、过程、验收、模板、Skill）都建立在这张卡上。

从一个真实场景开始 ​

两次请求的对比（都是让 Agent 整理材料）：

模糊版：「帮我整理一下这些资料，做个总结。」

结果：Agent 自由发挥，总结了所有 40 份文件，生成了 20 页内容，没目录、没重点、没边界。你还得自己重写。

任务卡版：

目标：产出「AI Agent 选型」主题的 3 页对比总结，供零基础同事阅读。 上下文与材料：material/ 下 8 份产品文档（见附件清单）；目标是选型对比，不讨论模型原理。 范围与约束：只读 material/；不联网；不修改任何原文件；输出到 output/。 交付物：output/01-summary.md（3 页内、含对比表）。 验收标准：覆盖全部 8 份材料；每款产品有「适合谁」一句话；表格列为产品/价格/门槛/适合人群；无虚构数据。

结果：Agent 一次产出符合要求的文档，你只花了 10 分钟核对。

差别的本质：你把「判断」提前做完了，Agent 只剩「执行」。

先说结论 ​

  1. 任务卡六要素：目标、上下文、输入材料、范围与约束、交付物、验收标准——缺一个，Agent 就要猜一次；
  2. 写卡花 5 分钟，返工省 50 分钟：把模糊需求变成明确指令，是新手到熟练用户的第一道分水岭；
  3. 验收标准必须可检查：「写得好」没法检查，「包含对比表、覆盖 8 份材料、无虚构数据」能检查；
  4. 禁区必须写进范围与约束：第 2 章的「绝不能让它做的事」，在这里变成明文；
  5. 任务卡是可复用资产：同类任务改改参数就能再用（第 12 章模板化的基础）。

必要概念 ​

  • 任务卡（Task Brief）：结构化的任务描述文档，六要素齐全。白话解释：给 Agent 的「工作单」，像给装修师傅的施工单一样具体。
  • 验收标准（Acceptance Criteria）：可逐项打勾的完成条件。白话解释：检查单，满足才算完工。
  • 约束（Constraints）：允许什么、禁止什么。包括范围（读哪些）、权限（能否联网/删除）、格式、时间等。

任务卡六要素详解 ​

要素回答的问题写卡要点反面例子
目标要达成什么？一句话，含主题与用途「做个总结」（为谁做？几页？）
上下文Agent 需要知道什么背景？背景、读者、口径、术语约定不给背景让它猜
输入材料用什么来做？明确文件/路径/清单，说明每个的作用「这些资料」（哪些？在哪？）
范围与约束允许做什么、禁止什么？读取范围、输出位置、可否联网、禁区不写边界
交付物交什么、在哪？文件名、格式、数量、位置「给我结果」（什么结果？）
验收标准怎样算合格？可检查的逐项条件「做得好一点」（无法检查）

跟着做：把「任务种子」写成任务卡 ​

第一步：填目标 ​

用一句话写：做什么 + 为谁做 + 做到什么程度。

例：把 material/ 里的产品材料整理成一份「选型对比」文档，供零基础读者 10 分钟读完。

第二步：填上下文 ​

写 Agent 必须知道、但材料里没有的背景：读者是谁、用途、口径（比如「对比价格时只用人民币」「不讨论技术原理」）。

第三步：填输入材料 ​

列出材料清单与每个材料的用途。材料不足时先补材料，不要指望 Agent 自己去找（第 11 章）。

第四步：填范围与约束 ​

  • 读取范围：只读 xxx/；
  • 写入范围：输出到 xxx/，不修改原文件；
  • 联网：允许/禁止；
  • 禁区：第 2 章写下的三条「绝不能做的事」。

第五步：填交付物 ​

精确到文件名、格式、数量、位置。让 Agent 先报交付清单再开始，能防遗漏。

第六步：填验收标准 ​

写出「逐项打勾」的标准。自检合格的验收标准通常满足：可数（8 份材料全覆盖）、可查（表格列为…）、可证（无虚构数据，来源标注）。

第七步：检查「假想敌」测试 ​

假想一个爱偷懒的 Agent，读你的卡：它会不会漏做某件事？会不会不知道该不该联网？会不会不知道输出到哪？任何「它可能会猜」的地方，就是卡没写清的地方。

一个完整示例（任务卡全文） ​

目标：整理 input/ 下 7 份「AI Agent 教程」材料，输出 6 份指定文档，用于教程项目的一轮基准测试。

上下文：材料来自真实教程项目；目标读者为零基础；对比口径：Qoder/TraeWork/ZCode 只使用中国版资料；不讨论模型原理，只记录产品体验。

输入材料：input/ 下 7 个文件（项目简报、笔记、读者反馈、产品事实表、流程图、输出要求清单）。注意：输入范围外的一切内容视为不存在。

范围与约束：只读 input/；输出到 output/；不联网；不修改任何输入文件；不删除任何文件；不把 Claude 封号原因写成确定事实。

交付物（输出到 output/）：01-project-summary.md、02-information-gaps.md、03-tutorial-outline.md、04-writing-plan.md、05-todo.md、06-self-check.md。

验收标准：6 份文件全部存在；每份文件按 OUTPUT-REQUIREMENTS.md 要求结构；信息缺口区分「事实/推断」；目录需说明是提案而非定稿；自检需列出输入文件清单与权限边界；不虚构数据。

这张卡就是第 5 章七款产品统一实测用的真实任务卡（完整协议见 ../../docs/08-common-benchmark-task.md），七款产品按它执行的结果见第 6 章选择表。

常见错误与恢复方法 ​

现象可能原因怎样修正
Agent 交的内容方向不对目标没说清用途/读者补「为谁做、做到什么程度」
材料没找全输入材料清单缺失先补材料清单，再发任务
它联网乱搜没写「禁止联网」约束里写清联网策略
改了原文件没写「只读」约束写死写入范围
交付物缺件没列交付清单交付物字段精确到文件名，让它先报清单
反复返工验收标准模糊把「感觉」翻译成「可检查项」

安全提醒 ​

  • 任务卡里不要粘贴敏感信息；需要引用时写「见文件 xxx」；
  • 高风险动作（发送/发布/付款/删除）不要写进「自动执行」，要写成「生成内容 + 人工确认后由人执行」；
  • 约束字段是授权的边界：没写进约束的，一律视为默认禁止，是最稳妥的安全策略。

本章练习 ​

25 分钟：把序章任务写成一张完整任务卡（六要素 + 假想敌测试）。完成后，如果你已选好产品（第 6 章），可以带着这张卡去跑第一次真实任务；如果还没选好，先保存，第 8、9、10 章会继续教你怎么安全地跑、怎么验收。

你应该带走的成果 ​

  • 第一张可执行任务卡（六要素完整）——这是后续所有章节的操作底座。

本章小结 ​

  1. 「帮我做一下」是失败句式，任务卡是成功句式；
  2. 六要素：目标、上下文、材料、约束、交付物、验收标准；
  3. 验收标准必须可逐项打勾；
  4. 禁区写进约束，未授权视为禁止；
  5. 任务卡是模板库的第一件资产（第 12 章）。
