第 15 章：Harness 是什么 ​

本章解决什么问题 ​

到第四篇为止，你有了任务卡、模板、Skill、规则——一个个「零件」。本章把这些零件组装起来看：Agent 真正的工作系统（Harness）长什么样。你将理解：为什么同样的模型，在不同产品里表现不同；为什么「模型很强」不等于「结果可靠」。产出：个人 Harness 草图。

从一个真实场景开始 ​

第 5 章实测里，两款产品用了同一个模型（DeepSeek V4 Flash，都通过 OpenCode Go），但表现明显不同：

  • ZCode 的审查视图把每份文件的增删行数列得清清楚楚（+46、+37、+84），变更透明性最强；
  • Hermes 把文件写错了目录，但自动发现、自动恢复、自动复核——恢复能力唯一实证。

模型一样，系统不同。 让它们产生差异的，不是「大脑」，而是「工作台」：工具怎么组织、权限怎么控制、状态怎么记录、验证怎么做——这套「工作台」就是 Harness。

先说结论 ​

  1. Harness 定义：把 Agent、上下文、工具、权限、状态、验证、反馈组织成一个工作系统的整体。白话解释：给 AI 配的「工作岗位 + 流程 + 规矩」，而不只是一个聊天框；
  2. 从「一个模型」到「一个工作系统」：单用模型像请了个聪明人但没给办公桌；Harness 是给聪明人配齐办公桌、流程、门禁和质检；
  3. 七要素各司其职：Agent（执行者）、上下文（视野）、工具（手脚）、权限（门禁）、状态（进度）、验证（质检）、反馈（复盘）；
  4. Harness 决定三件事：可靠性（稳不稳）、成本（贵不贵）、体验（顺不顺）——比模型选择影响更大；
  5. 你已经在用 Harness 了：第 1–14 章攒的零件（任务卡、权限卡、CONTEXT、模板、Skill、规则）组装起来，就是你的个人 Harness——本章只是把它「显影」出来。

必要概念 ​

  • Harness：围绕模型搭建的工作系统。白话解释：模型是发动机，Harness 是整辆车——底盘、方向盘、刹车、仪表盘。
  • 回路（Loop）：理解 → 行动 → 反馈 → 修正 的循环（第 1 章流程图）。Harness 是把回路「制度化」：每一步该看什么、该停哪、该验什么。
  • 状态（State）：任务的进度信息（第 11 章状态文件）。Harness 负责维护和传递状态，避免「失忆」。
  • 验证（Verification）：Harness 内置的检查机制（自检、验收清单、哈希校验）。注意：验证机制本身也需人工抽查（第 2、10 章教训）。

Harness 七要素一览 ​

要素负责什么你已有的资产
Agent执行任务的主体（产品 + 模型）第 5 章选的产品
上下文给 Agent 视野CONTEXT.md（第 11 章）
工具让 Agent 动手产品工具 + 你的 Skill（第 13 章）
权限控制边界权限分级表（第 8 章）
状态记录进度状态文件/复盘记录（第 10、11 章）
验证保证质量验收清单（第 10 章）
反馈沉淀改进规则/模板/技能迭代（第 12–14 章）

跟着做：画你的个人 Harness 草图 ​

第一步：画七个盒子 ​

在白纸上按「流程」排列七要素：上下文 → Agent → 工具 →（动作）→ 验证 →（输出）→ 反馈 → 状态。权限盒子横跨在「Agent 的工具使用」上方（表示门禁）。用箭头画出信息流。

第二步：在每个盒子里写「我现在用什么」 ​

  • 上下文：CONTEXT.md？
  • Agent：哪款产品（第 6 章选的）？
  • 工具：有哪些 Skill？
  • 权限：用哪级？谁确认？
  • 状态：状态文件在哪？
  • 验证：验收清单有几项？
  • 反馈：复盘记录更新了吗？

第三步：找出「空盒子」 ​

哪个盒子你还没有对应资产？比如「验证」只有模糊感觉没有清单——那就是下一章的改进点。

第四步：标注「人工检查点」 ​

在图里标出你必须在场的节点（高风险动作、最终发布、验收打勾）。Harness 不是「全自动机器」，是「人机协同的流水线」。

一个完整示例（第 5 章实测的 Harness 观察） ​

统一基准任务的 Harness 运行观察（各产品表现见第 6 章选择表）：

  • 上下文：7 份材料 + 统一任务卡 → 决定了「输入范围」；
  • 权限：多数产品无弹窗执行；Qoder/Hermes 越权读取——权限环节是它们的短板；
  • 状态：有的产品把「测试已完成」当成未完成（上下文不足导致）——状态传递失败；
  • 验证：自检质量差异巨大——Codex 覆盖 7 份输入，Qoder 称「全部通过」却漏报越界；
  • 反馈：验收记录（run-record）成为第 6 章评分的证据——反馈闭环生效。

结论：同一个任务，Harness 强弱决定了「能否一次通过」和「边界是否守得住」。模型几乎一样，结果差异巨大。

常见错误与恢复方法 ​

现象可能原因怎样修正
换了个更强的模型，问题依旧问题在 Harness 不在模型检查七要素，先补验证/权限短板
Harness 画得越复杂越安心误解了「系统化」最小可用：先保证闭环，再谈复杂
全自动化，出事才后悔没标人工检查点高风险节点必须有「人在场」标记
状态没人维护，任务反复丢进度状态盒子空了用 CONTEXT.md + 状态文件补上
以为 Harness 是「买来的产品」误解Harness 是你自己组装的系统，产品只是 Agent 要素之一

安全提醒 ​

  • Harness 草图里标注的权限边界、人工检查点，要能落到第 8 章权限卡的「允许/禁止」清单；
  • 不要为了「自动化」省略验证——验证被自动化跳过，错误就会被放大（第 14 章杠杆）；
  • Harness 中任何「自动执行外部动作」的设计，都必须保留人工最终确认。

本章小结 ​

  1. Harness 是围绕模型的工作系统，决定可靠性、成本与体验；
  2. 七要素：Agent、上下文、工具、权限、状态、验证、反馈；
  3. 同一个模型在不同 Harness 里表现不同（实测证据）；
  4. 你已经拥有 Harness 的零件，本章把它们显影成图；
  5. 下一章讲 Harness 的架构设计（第 16 章）。
