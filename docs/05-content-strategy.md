# 内容策略与体验评测方案

## 推荐的整体叙事

教程采用“选择 → 会用 → 用稳 → 定制 → 系统化”的递进路线：

1. **选择**：认识不同 Agent，通过真实体验选出适合自己的工具；
2. **会用**：完成范围明确、风险可控的第一个任务；
3. **用稳**：掌握上下文、权限、过程跟进、验收和复盘；
4. **定制**：把重复需求沉淀为规则、模板和 Skills；
5. **系统化**：用 Harness 组织工具、记忆、权限、验证与反馈；
6. **应用**：进入内容创作、代码编写、工作流等完整案例。

这条路线保留“先从软件体验入手”的亲和力，同时为 Skill 和 Harness 提供必要铺垫。

## 第一部分：整体构想与软件体验

### 统一使用桌面图形界面版本

教程中的七款 Agent 均以桌面 GUI 版本为体验对象，不以 CLI 或 TUI 作为演示入口。评价不仅关注最终能力，也关注新手能否顺利完成下载安装、账号登录、首次授权、文件选择、任务观察、结果定位和错误恢复。

软件后台是否使用命令行、云端或本地服务单独记录，但不要求普通读者直接操作。若某项能力只能通过命令行完成，应明确标记为不属于主教程的基础体验。

### 先解释产品类型，再比较产品

七款 Agent 的定位和交互方式未必完全相同。开始横向比较前，需要先说明它们属于哪种形态、主要在哪个环境工作、能接触什么资料。否则读者可能把适合不同任务的产品放在同一条总分榜上。

对新手可以先用四组建立直觉：

1. 海外闭源托管型综合 Agent：Claude、Codex；
2. 国内综合型 Agent：TreeWork、Work Buddy；
3. 代码优先型 Agent：Qoder、Z Code；
4. 开源自主型 Agent：Hermes。

这四组适合组织文章，但不应作为唯一比较轴。实际选型还要叠加任务方向、开放程度、后台运行方式、自主程度和使用门槛等标签。

### 建立统一体验协议

每款 Agent 至少完成三类任务：

1. **共同基准任务**：所有产品使用相同材料和验收标准，用于观察差异；
2. **优势任务**：选择最能体现该产品特点的任务；
3. **边界任务**：验证它在哪些条件下容易失败或需要人工介入。

每次体验记录：

- 测试日期、桌面客户端版本、操作系统和硬件环境；
- 下载来源、安装过程、登录方式和首次启动体验；
- 免费版或付费版，以及实际可见的额度限制；
- 输入材料、完整任务描述和验收标准；
- 完成时间、人工介入次数和是否成功；
- 关键截图、失败表现和恢复方式；
- 界面导航、字号可读性、状态反馈和权限提示是否容易理解；
- 事实记录与个人感受分别表述。

### 免费额度需要特殊处理

免费额度是读者关心、同时也最容易变化的信息。建议：

- 页面显著标注“最后核验日期”；
- 优先链接官方价格或帮助页面；
- 不只写次数，还解释重置周期、模型限制和功能限制；
- 无法核实时明确写“以官方当前页面为准”；
- 把价格和配额放在便于单独更新的数据区，不散落在长文各处。

### 让截图承担明确任务

截图应服务于以下目的之一：展示入口、解释操作、证明结果、比较差异或说明风险。避免只为丰富页面而截图。

每张截图应包含：

- 简短图注；
- 截图日期或适用版本；
- 必要的序号、框选或箭头；
- 对账号、文件名、密钥和个人信息的脱敏；
- 供无障碍阅读使用的替代文字。

## 第二部分：个性化与精细化操作

### 增加一段能力阶梯

不要从产品介绍直接跳到 Skill 和 Harness。建议按以下顺序展开：

> 普通对话 → 清晰任务卡 → 上下文与权限 → 验收与复盘 → 模板 → 项目规则 → Skill → Harness → 多 Agent

每一级都应回答两个问题：它解决了上一级的什么重复问题，以及是否值得为此增加复杂度。

### 以真实案例承载抽象概念

个人内容创作、代码编写和工作流搭建，都采用相同的案例结构：

1. 原始任务与旧做法；
2. 为什么选择这个 Agent；
3. 提供了哪些上下文和权限；
4. 第一次执行发生了什么；
5. 怎样验收、修正和复盘；
6. 最后沉淀了什么模板、Skill 或 Harness 组件。

这样读者看到的是设计过程，而不只是一个难以照搬的最终配置。

### Skill 与 Harness 的术语策略

- 第一次出现时先用白话解释；
- 明确它们不是所有读者都必须使用；
- 提供“最小版本”和“进阶版本”；
- 同一个概念尽量展示跨 Agent 的共通原则；
- 产品专属配置放在独立说明或附录中。

## 第三部分：现在就应做的网站化准备

部署方式和视觉设计可以后置，但以下内容结构会影响全部写作，建议现在固定：

- 每篇文章只负责一个明确主题；
- 使用稳定、可读的文件名和页面路径；
- 记录标题、摘要、适合人群、难度、更新时间和标签；
- 图片与正文分离保存，采用统一命名；
- 产品事实、作者体验和教程步骤在版式语义上可区分；
- 每篇文章预留“上一步、下一步、更新时间、反馈入口”；
- 所有图片提供替代文字，页面不能依赖图片才能理解；
- 把易变的产品信息与相对稳定的方法论内容分开。

这些约定不会决定最终采用哪一种网站技术，但能显著减少之后迁移内容的成本。

## 还需要补充的四个机制

### 1. 读者决策机制

产品体验的终点不是“全部了解”，而是得出选择。需要提供按人群、任务和限制进行判断的选择矩阵或决策树。

### 2. 内容更新机制

为产品页面记录最后核验日期和更新状态。建议每季度快速复核一次，重大版本发布时单独更新。

### 3. 可信度机制

清晰标记官方事实、实测结果、个人判断和推测。如果未来存在赞助、推荐链接或厂商提供的账号，也应显著披露。

### 4. 新手验证机制

正式发布前邀请零基础读者试读。重点观察他们在哪里看不懂、在哪里不敢操作、在哪里无法复现，而不只询问“觉得写得好不好”。

## 建议的最小发布版本

第一版不必等待全部 23 章写完，可以先发布：

1. Agent 是什么，以及能力与边界；
2. 选择 Agent 的统一维度；
3. 七款产品的简版体验卡；
4. 如何写一张任务卡；
5. 如何验收 Agent 的结果；
6. 一个完整的工作或生活案例；
7. 一篇从模板走向 Skill/Harness 的预告文章。

这个版本已经能形成完整读者闭环，也能尽早获得真实反馈。
