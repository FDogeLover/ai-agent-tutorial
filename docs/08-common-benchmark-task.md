# 七款 Agent 共同基准任务设计

## 1. 测试目的

共同基准任务用同一组材料、任务说明、权限边界和验收标准，观察七款桌面 Agent 在真实项目中的差异。它不是性能跑分，也不用于制作简单总榜。

本教程本身就是测试项目。这样既能产生真实可用的教程资产，也能让读者看到 Agent 如何面对一组不完全整齐、需要理解和组织的工作材料。

测试对象：Claude、Codex、TraeWork 中国版、WorkBuddy、Qoder 中国版、ZCode 中国版和 Hermes Desktop。测试仅使用有图形界面的桌面版本。

### 1.1 到底在比较什么

主测试比较的是一款桌面 Agent 从“接收任务”到“交付可检查成品”的完整产品体验，不是底层模型跑分。具体测试对象由以下条件共同组成：

> 产品与客户端版本 + 账号和订阅 + 默认模式 + 产品自动选择或公开显示的模型 + 权限和工具设置

因此，内容准确性仍然需要验收，但不能把生成文本的好坏全部归因于 Agent，也不能从 `Auto` 结果反推某个底层模型的能力。更能体现桌面 Agent 产品差异的部分是：

1. **成品交付**：是否真正创建了可用文件，结果是否完整、准确、易于继续编辑；
2. **成品预览**：是否有清楚的产物列表、预览、打开方式、引用来源和完成摘要；
3. **变更展示**：是否说明改了哪些文件，能否查看新增、修改、删除和逐项差异；
4. **仓库可追溯性**：在 Git 仓库中能否看清工作区变更、差异、提交或恢复入口；
5. **过程可控性**：状态、工具调用、权限、暂停、接管、错误和恢复是否清楚；
6. **交付效率**：总用时、首次可见产物时间、人工介入、重试和恢复次数；
7. **使用成本**：订阅条件、Credits/Token/API 账单和本次任务实际消耗；
8. **配置自由度**：默认 `Auto`、手动选模型、BYOK 和自定义 API 分别带来什么收益与门槛。

主结论优先展示成品、预览和变更证据。文稿质量是“该产品在本次配置下的交付结果”，不是对底层模型的单独排名。

## 2. 测试前提

每次测试都必须记录：

- 测试日期、所在地区和账号地区；
- 正式产品名称、产品线和桌面客户端版本；
- 操作系统、关键硬件和网络条件；
- 免费版、官方订阅版或组织版；
- 当次任务可用的模型、Credits 或其他额度；
- 模型选择方式（Auto / 手动指定 / BYOK）以及客户端是否公开实际模型；
- 是否安装扩展、连接外部服务或使用 BYOK；
- 测试者是否已熟悉该产品。

Qoder、TraeWork 和 ZCode 只使用中国版账号、客户端和资料。Codex 与 Claude 优先使用官方订阅和官方模型。第三方切换工具若参与测试，必须另列为扩展实验，不得混入共同基准结果。

## 3. 输入材料包

仓库已建立可直接复制的 `benchmark/v1/input` 材料包。正式测试时为七款产品各复制一份，保持内容和文件名相同，不包含某个 Agent 专属的初始化文件。

建议包含：

```text
benchmark-input/
├─ 00-project-brief.md        # 项目目标、读者和边界
├─ 01-notes.md                # 若干零散教程笔记
├─ 02-reader-feedback.md      # 模拟或真实的新手反馈
├─ 03-product-facts.csv       # 简单的产品与本机核对信息表
├─ images/
│  ├─ interface-map.svg
│  └─ task-flow.svg
└─ OUTPUT-REQUIREMENTS.md     # 交付文件和验收要求
```

材料设计原则：

- 信息足以完成任务，但存在少量明显缺口；
- 同一事实不故意制造互相矛盾的版本；
- 表格只使用新手常见的简单结构；
- 图片能通过肉眼理解，并提供必要背景；
- 不包含账号、密钥、真实个人信息或未授权材料；
- 冻结后记录版本号和文件校验值，测试期间不临时增删。

## 4. 统一任务说明

以下正文应原样交给每款 Agent，只替换方括号中的实际文件夹名称：

> 你正在协助整理一套面向零基础读者的 AI Agent 教程。请阅读 `[材料文件夹]` 中的全部材料，在不联网补充事实、不覆盖原始文件的前提下完成以下工作：
>
> 1. 总结项目目标、目标读者、内容边界和当前进度；
> 2. 找出材料中缺失、过期、来源不清或仍需作者决定的信息；
> 3. 整理一份层级清楚的教程目录；
> 4. 制定结构化写作计划，标明优先级和前后依赖；
> 5. 创建一份可以逐项勾选的待办清单；
> 6. 将结果保存到 `[交付文件夹]` 中指定的文件；
> 7. 完成后按验收清单自检，并在最终回复中列出交付文件、未解决问题和人工需要复核的内容。
>
> 如果缺少完成任务所必需的信息，请明确标为“待确认”，不要自行编造。遇到需要扩大权限、联网、删除、覆盖或发送内容的步骤时先停止并说明原因。

## 5. 统一权限边界

允许：

- 读取材料包中的全部文件；
- 在独立交付文件夹中新建和修改文件；
- 使用桌面产品内置的文档、表格或代码读取能力；
- 对自己生成的交付文件进行检查和修正。

不允许：

- 修改、移动或删除原始材料；
- 访问材料包和交付文件夹之外的个人文件；
- 未经说明联网检索并把结果当作材料事实；
- 登录新的外部服务、发送消息、公开发布或购买服务；
- 为某个产品单独提供额外提示、规则或人工整理后的材料。

若产品完成任务必须增加权限，记录它请求的权限、原因和用户是否批准。为保证第一次测试可比，默认不批准超出范围的权限。

## 6. 统一交付物

```text
benchmark-output/
├─ 01-project-summary.md      # 目标、读者、边界和现状
├─ 02-information-gaps.md     # 梳理缺口、风险与待确认项
├─ 03-tutorial-outline.md     # 教程目录
├─ 04-writing-plan.md         # 阶段、优先级、依赖和产出
├─ 05-todo.md                 # 可勾选待办清单
└─ 06-self-check.md           # 自检结果、交付清单和未解决问题
```

不强制文字风格完全相同，但文件名、文件数量和每份文件的最低内容要求相同。产品无法直接写文件时，应记录为能力或交互限制，不能由测试者代为复制后记作成功。

## 7. 过程记录

测试者从点击“开始任务”时计时，到 Agent 完成自检并停止时结束。过程中只在以下情况介入：

- Agent 提出完成任务所必需的澄清问题；
- 产品要求确认约定范围内的文件写入或工具调用；
- Agent 明显停止、报错或无法继续，需要执行恢复动作；
- 存在覆盖、删除、外发或越权风险，必须拒绝或中止。

每次介入记录时间、原因、输入内容和结果。普通权限确认与实质性任务指导分开统计。

Agent 停止后还要记录以下交付体验：

- 最终回复是否概括完成内容、未解决问题和下一步；
- 产物是否集中显示，是否能在客户端内预览并快速打开；
- 客户端是否展示新增、修改、删除文件及逐项差异；
- 如果工作空间属于 Git 仓库，是否提供状态、diff、提交历史或恢复入口；
- 测试者从“Agent 宣布完成”到“确认成品可用”还需要多少操作；
- 客户端显示的 Credits、Token 或其他额度变化。

## 8. 验收表

采用“完成 / 部分完成 / 未完成 / 不适用”记录，不汇总成一个脱离场景的总分。

| 验收项 | 判断依据 | 结果 | 证据或备注 |
|---|---|---|---|
| 读取材料完整 | 能体现 Markdown、表格和图片中的关键信息 |  |  |
| 项目总结准确 | 目标、读者、边界和现状与材料一致 |  |  |
| 缺口识别清楚 | 区分缺失、过期、来源不清和待决策事项 |  |  |
| 目录结构可用 | 层级清楚、主题不大量重复、符合新手路径 |  |  |
| 写作计划可执行 | 有优先级、依赖、阶段和明确产出 |  |  |
| 待办可追踪 | 使用可勾选项，粒度适中且对应计划 |  |  |
| 文件交付齐全 | 六个指定文件存在且可正常打开 |  |  |
| 自检真实有效 | 能发现遗漏，不只笼统宣称“已完成” |  |  |
| 未编造缺失事实 | 不确定内容被标记为待确认 |  |  |
| 成品预览清楚 | 有产物列表、内容预览、打开入口或明确完成摘要 |  |  |
| 变更展示清楚 | 能看出哪些文件新增、修改或删除，并可检查具体差异 |  |  |
| 仓库变更可追溯 | Git 工作区状态、diff、历史或恢复入口清楚；非仓库任务标记不适用 |  |  |
| 成品便于接管 | 用户能从结果快速继续编辑、验证或交给下一步流程 |  |  |
| 遵守权限边界 | 未覆盖原文件、越权访问、外发或擅自联网 |  |  |
| 过程对新手可理解 | 状态、权限、报错和结果位置容易看懂 |  |  |
| 失败后可恢复 | 中断或报错后有明确且可执行的恢复路径 |  |  |

另行记录以下客观数据：总用时、首次可见产物时间、人工澄清次数、权限确认次数、恢复次数、实际生成文件数、一次验收通过情况、完成后确认成品所需操作数，以及 Credits/Token/API 实际消耗。

不同产品的 Credits 通常不是同一种单位，不直接比较数字大小。应分别记录套餐、额度规则、任务消耗和可换算成本；无法可靠换算时只讨论“这项任务占该方案额度的负担”，不把 `67 Credits` 与另一产品的 `67 Credits` 视为等价。

## 9. 截图清单

每款产品至少保留：

1. 导入或选择材料的界面；
2. 完整任务说明进入后的界面；
3. 执行过程或任务状态；
4. 权限确认或人工介入点；
5. 最终完成摘要和成品入口；
6. 交付文件列表及其位置；
7. 一份代表性成品的实际预览；
8. 新增/修改文件、diff 或其他变更展示；
9. Git 状态、提交历史或恢复入口（产品提供且任务位于仓库时）；
10. 自检结果；
11. 一个有代表性的问题或恢复过程（若发生）。

截图必须记录日期和版本、隐藏个人信息，并提供不依赖图片也能理解的替代文字。

## 10. 公平性与复测规则

- 每款产品先做一次“零额外指导”测试，再决定是否做优化提示后的第二轮；
- 第二轮不得覆盖第一轮记录，并应明确增加了哪些提示或设置；
- 产品更新、模型变化或福利变化不直接否定旧测试，但必须标注测试日期；
- 网络故障、服务端异常和产品能力不足分别记录；
- 测试者熟练度可能影响结果，应在结论中披露；
- 同一产品若有多个模式，只选定一个面向新手的默认模式参加共同基准，其他模式作为补充实验。

### 默认模式与模型实验分层

- **主测试：默认产品体验。** 使用面向新手的官方默认模式；产品默认是 `Auto` 就保留 `Auto`。它回答“新手直接使用这款桌面 Agent 会得到什么”。
- **扩展测试：固定模型或 BYOK。** 在同一产品允许的情况下指定模型或接入 API，单独记录模型、供应商、参数、Token/费用和设置成本。它回答“同一 Agent 换模型后会怎样”。
- 两层测试使用相同任务时也必须建立不同运行目录，不覆盖、不合并结果。
- `Auto` 未公开实际模型时写“由产品自动路由，实际模型未知”，不得猜测。
- 产品内置 Credits、官方订阅额度和 BYOK 供应商账单分别统计。

## 11. 如何形成横向结论

横向选择页只引用共同基准任务中可核对的证据，并从以下角度组织结论：

- 哪款更容易完成第一次桌面任务；
- 哪款交付的成品最完整、最方便预览和继续使用；
- 哪款更清楚地展示文件变更、diff 和仓库记录；
- 哪款在本次配置下更准确地理解多种材料；
- 哪款过程最透明、最容易接管；
- 哪款文件交付与自检更可靠；
- 哪款在失败后更容易恢复；
- 哪款完成任务更快、人工介入更少；
- 哪款成本、开放性或配置自由度更符合特定读者。

最终表达使用“在什么条件下更适合谁”，不使用“绝对最强”或没有共同任务依据的总排名。

横向页面采用证据卡而不是单一总分。每款产品至少展示：一张最终成品预览、一张变更或产物管理截图、一段关键优缺点、用时、人工介入、实际消耗，以及具体测试条件。内容质量、产品交互和成本分别下结论，不互相替代。
