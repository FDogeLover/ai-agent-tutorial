# 写作与内容规范

## 读者假设

- 不假设读者会编程；
- 不假设读者知道模型、上下文窗口、API、MCP、Skill 或 Harness；
- 第一次出现术语时，用一句白话解释，再给正式定义；
- 必要操作给出界面路径、输入示例和预期结果；
- 主教程不要求读者使用 CLI/TUI；无法避免的命令行内容放入选读附录，并解释用途、风险和撤销方式。

## 章节结构

每一章尽量回答以下问题：

1. 这一章能帮助读者解决什么问题；
2. 为什么会有这个问题；
3. 最小必要概念是什么；
4. 应该怎样操作；
5. 有哪些常见错误和风险；
6. 如何判断结果是否合格；
7. 本章产生什么可复用成果。

## 网站化元数据

开始写正式章节时，为每篇文章记录以下信息，具体网站技术确定后再转换成对应格式：

- 稳定页面标识；
- 标题与一句话摘要；
- 适合人群与前置知识；
- 难度和预计阅读时间；
- 创建日期、最后核验日期；
- 内容标签；
- 是否包含易变的产品信息。

## 表达原则

- 先给结论，再解释原因；
- 优先使用短句、具体动作和真实例子；
- 不堆叠产品宣传语和技术术语；
- 不把一次成功经验写成普遍规律；
- 明确区分事实、个人体验、推测与建议；
- 对新手可能遇到的失败给出恢复路径。

## 产品相关内容

产品变化很快，介绍具体 Agent 时必须：

- 标注体验日期、操作系统、桌面客户端版本和实际运行方式；
- 使用统一的任务和观察维度；
- 把事实能力与作者偏好分开写；
- 避免只给总分或“最好用”结论；
- 价格、配额和功能变化尽量链接官方来源；
- 说明选择结论适用的人群和前提。

### 区分产品、Agent 与模型

本教程的实际测试对象统一为桌面图形界面产品。文章仍要写清楚具体客户端、版本、操作系统和后台运行方式。除非确实在比较模型本身，否则不要用“模型”代替整个 Agent 产品。

带有“国内”“海外”“开源”“闭源”等标签时，要说明标签描述的是产品团队、服务方式、源代码还是模型权重，避免把不同概念混在一起。

## 真实经验的写法

推荐采用“变化过程”而不是只展示成品：

> 原来的做法 → 出现的问题 → 如何判断原因 → 做了什么修改 → 怎样验证 → 最终沉淀了什么

涉及 Skills 或 Harness 时，应展示：

- 它源自哪个重复问题；
- 为什么普通提示词不够；
- 核心结构和边界；
- 一次实际执行过程；
- 已知限制与后续改进。

## 安全与伦理

- 示例中去除真实密钥、账号、地址和敏感数据；
- 涉及发送、发布、购买、删除和付费时设置人工确认点；
- 医疗、法律、财务等高风险内容明确提示专业复核；
- 不用虚构引用支撑结论；
- 尊重软件许可、内容版权和组织政策。

## 建议长度

- 概念章：2,000—4,000 字；
- 操作章：3,000—6,000 字；
- 产品体验：每款 1,500—3,000 字；
- 完整案例：3,000—8,000 字；
- 快速卡片：单页即可使用。
