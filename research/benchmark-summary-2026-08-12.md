# 桌面 AI Agent 共同任务阶段汇总

> 数据日期：2026-08-12  
> 当前状态：内容交付验收已完成；产品内预览、变更展示与 Git/恢复体验仍待统一截图验收。

## 1. 这次横评在比较什么

本轮比较对象不是单独的底层模型，而是桌面 AI Agent 的端到端交付能力：用户把同一份材料和同一项任务交给产品后，它能否在尽量少的人工介入下，生成完整成品，并让新手方便地预览、核对、修改和恢复。

因此，最终评价由以下几部分共同组成：

1. 成品是否完整、可继续使用；
2. 成品预览、文件列表和打开入口是否清楚；
3. 新增、修改、删除内容及逐文件差异是否容易核对；
4. 权限策略是否易懂，实际执行需要多少人工介入；
5. 是否遵守读取和写入边界，自检能否发现真实问题；
6. 任务完成速度、成本及成本透明度；
7. 出错后能否说明问题并恢复；
8. 对零基础用户的配置和维护门槛。

模型、Provider、推理强度会影响结果，必须随运行配置一起记录，但不把内容质量直接写成某个模型的单独成绩。

## 2. 测试边界

- 只测试 Windows 桌面图形界面，不评价 CLI 或 TUI。
- 所有可运行产品使用同一份冻结材料包和同类提示词。
- 指定交付为 6 份 Markdown；输入基线为 7 个文件。
- benchmark v1 已冻结，不因某款产品的表现回改。
- QoderWork CN 是追加的扩展样本，后续可在 benchmark v2 中正式纳入。
- Agent 生成的教程目录只是基准答卷，不能覆盖仓库的正式 23 章框架。
- 不同产品的 Credits/积分不是统一单位，只保留各自的原始数值，不按数值直接横向排名。
- ZCode 和 Hermes 使用外部 Provider，其速度、质量与成本应归因于“桌面 Agent + Provider + 模型 + 推理设置”的组合。
- Claude 因测试账号受限未进入共同任务；这只是作者个人遇到的可用性阻断案例，不能推导普遍封号率。

## 4. 分层解读

### 4.1 官方或产品托管路径

WorkBuddy、TraeWork、Qoder CN、QoderWork CN 和 Codex 均使用产品内提供的任务路径。本层更接近新手开箱使用场景，但五款产品的模型选择、费用展示和订阅机制并不相同，不能视为完全相同的实验条件。

目前可以确认：

- Qoder CN 的界面记录用时最短，并明确展示 Credits 和人民币费用；这只代表本账号、本版本与本轮 Auto 配置。
- QoderWork 同样较快，但同一轮有两条计费记录，需要用截图保留原始事实，不推断各自对应的内部阶段。
- WorkBuddy 和 TraeWork 均未要求人工介入；WorkBuddy 已确认支持成品预览和逐文件 diff，同时暴露了“产物 6 份、变更仅 5 份”的一致性问题。
- Codex 无人工介入且自检较完整，但客户端没有清晰给出本轮成本，成品预览和变更体验仍需截图后判断。

### 4.2 BYOK / 外部 Provider 路径

ZCode 和 Hermes 本轮都使用 OpenCode Go 与 DeepSeek V4 Flash，推理设置为最高。这有利于观察两款 Agent 在相近模型条件下的工程差异，但不能代表它们所有 Provider 或默认配置。

- ZCode 按“变更前确认”流程要求了权限确认和人工回复，控制感更强，但对新手增加了操作与概念门槛。
- Hermes 在用户无介入的情况下自动恢复了路径误写，体现了一定恢复能力；但智能审批没有阻止写入禁止目录，且任务读取范围超过 `input`，安全感不能仅凭“没有弹窗”判断。
- 两轮实际 API 成本均未记录，不能用“模型通常便宜”替代本轮成本证据。

### 4.3 账号可用性阻断

Claude 未获得与其他产品相同的共同任务成绩。教程中应把它放入“实际使用前的账号与地区可用性检查”案例，而不是强行补齐一行性能数据；也不能根据单一账号经历给出普遍风险概率。

## 5. 当前可下的结论

1. 七个可运行样本都完成 6/6 指定交付，最终输入哈希均为 7/7；单看“有没有生成文件”无法拉开差异。
2. Qoder CN 本轮最快，但读取边界和自检可靠性存在明显问题；速度不能替代交付可信度。
3. 0 次权限弹窗不等于严格限制访问范围。Qoder、QoderWork 和 Hermes 的结果都证明 Agent 可读取指定 `input` 之外的工作区文件。
4. Hermes 是唯一出现已记录内部路径偏差并自动恢复的样本；应同时保留“恢复成功”和“曾违反写入边界”两个事实。
5. ZCode 是唯一确认需要权限批准和人工回复的完整样本；精确次数未记录，不能补估。
6. 目前只有 WorkBuddy 已留下可核对的产品内预览和 diff 草稿证据。统一截图完成前，不宜发布总体排名或“最适合新手”的最终结论。
7. 下一阶段最重要的不是再跑一次内容生成，而是补齐每款产品的成品预览、变更展示、Git/恢复入口和配置可见性证据。

## 6. 后续评分建议

截图验收完成后，再按以下维度分别评分，不先合成为一个总分：

| 维度 | 建议关注点 |
|---|---|
| 交付成果 | 6 份文件是否完整、内容能否直接继续编辑与交接 |
| 预览体验 | 列表、Markdown 渲染、打开路径、阅读舒适度 |
| 变更核对 | 文件变更是否完整，是否有逐文件/逐行 diff，删除是否醒目 |
| 过程可控 | 权限文案、人工介入次数、停止与继续是否清楚 |
| 安全边界 | 读取/写入是否遵守提示，自检能否发现真实偏差 |
| 效率 | 端到端用时、必要操作数、是否需要重试 |
| 成本 | 原始 Credits/积分/API 费用，以及产品是否清楚展示 |
| 恢复与 Git | 错误说明、恢复入口、Git 状态/历史/回退能力 |
| 新手门槛 | 登录、模型、Provider、API、推理和权限概念的复杂度 |

各维度保留客观证据和作者体验两列，避免把“我觉得方便”写成不带依据的产品事实。
