## 一、缺失信息

### 1.1 产品实测数据

七款产品目前只有页面骨架和基础事实表，缺少统一任务下的实测数据。具体包括：

- 每款产品完成同一任务的**实际用时**、**Credits 消耗**、**操作步骤数**和**人工介入次数**均无记录（`run-record.md` 中相关字段全部为空）；
- 每款产品的**正式界面截图**尚未拍摄，现有两张 SVG 只是分类示意图和流程图，不能替代产品界面截图；
- 横向实测结论（哪些产品在哪些场景下表现更好）尚未得出。

### 1.2 登录与账号状态

- **Claude 桌面版**：作者账号已被封禁，具体原因尚未核实。材料中明确写了"不能把单个封禁案例推导为普遍封号率"，但目前既没有封禁原因的核实结论，也没有替代账号的登录体验记录。（来源：`01-notes.md`、`03-product-facts.csv`）
- **Codex 桌面版**：Windows 清单当前显示为 ChatGPT 而非 Codex 独立入口，统一任务尚未完成。（来源：`03-product-facts.csv`）
- 其他产品的账号登录状态、地区可用性和稳定性均标注为"待核对"或"待实测"。

### 1.3 新手安全边界

读者 B 的反馈明确提出"哪些按钮可以放心点，哪些操作会删除文件、花钱或把内容发出去"，但目前材料中没有针对任何一款产品的**安全操作指南**或**风险操作清单**。

### 1.4 Skill 和 Harness 的真实案例

读者 D 需要"第一次设计为什么失败，以及后来怎样调整"的真实案例，笔记中也提到"Harness 要通过一次失败和恢复说明它解决了什么问题"。目前这些案例尚未编写。

### 1.5 Credits、Token 和 API Key 的入门解释

读者 A 反馈"不太理解 Credits、Token 和 API Key 的区别"，但材料中没有对应的概念解释章节。笔记提到"价格、Credits、活动和账号可用性都容易变化，应该集中维护"，但尚未形成独立文档。

### 2.2 订阅方案与 Credits

WorkBuddy 的"每日积分属于账号当日可见活动，不视为永久权益"，TraeWork 的"Credits 与活动需复核"。所有产品的订阅价格、Credits 额度、促销活动和权益变动都属于高频变化信息，材料中尚未给出统一的维护策略或更新频率。

### 2.3 地区可用性

材料提到"如果软件在我的地区不能稳定登录"（读者 E），但没有列出每款产品在中国大陆的登录稳定性、网络要求和替代方案。

## 三、来源不清的信息

### 3.1 模拟反馈的代表性

`02-reader-feedback.md` 明确标注为"基准测试的模拟反馈，不是真实用户研究结论"。在正式教程中引用时，需要标注这是模拟反馈还是真实反馈，避免读者误以为是用户调研数据。

### 3.2 产品分类依据

`interface-map.svg` 将七款产品分为四类，但没有说明分类标准（按什么维度区分"综合型"与"代码优先型"、"海外闭源"与"开源自主"）。分类是否经过作者最终确认，材料中未体现。

### 3.3 产品事实表的验证状态

`03-product-facts.csv` 中"已知限制或待核对事项"一列混合了已确认事实（如"作者账号被封"）和待验证判断（如"配置自由度对新手的影响待实测"），但没有用统一标记区分哪些已经核实、哪些仍是传闻或推测。

## 四、仍需作者决定的事项

以下事项在 `01-notes.md` 中明确列出为"仍需作者决定"：

1. **第一批正式发布哪些章节**——决定了教程的 MVP 范围和读者第一印象中能看到的完整度。
2. **第一篇完整案例选择什么场景**——工作、生活、内容还是代码项目？不同场景面向的读者画像不同。
3. **网站使用哪种技术部署**——页面文件名、更新时间和图片替代文字已要求提前统一，但技术选型本身未定。
4. **是否邀请零基础读者参与测试**——如果邀请，如何收集反馈、样本量和筛选标准也需要确定。
