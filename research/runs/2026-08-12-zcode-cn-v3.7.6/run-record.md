## 测试者观察

### 容易理解的地方

- 六份文件按顺序生成，文件位置和命名符合提示要求。
- 变更前确认让写入行为显式经过用户批准，控制感强于无提示直接写入。

### 需要复核或可能让新手困惑的地方

- 当前 3.7.6 测试没有观察到统一 Auto 模式，需要先理解模型供应商、API、具体模型和推理强度。
- 权限确认与人工回复确实发生，但没有保留逐次数量和文案，暂时无法计算精确操作次数或评价提示是否友好。
- 产品内成品预览、变更 diff 和 Git/恢复入口尚待统一截图，当前不能评价这些核心交付体验。

### 只属于本轮结果、不能直接推广的判断

- 5 分 41 秒是 ZCode、OpenCode Go、DeepSeek V4 Flash、最高推理强度和变更前确认共同作用的结果，不能单独归因于 ZCode 或 DeepSeek。
- 外部 API 的模型效率和费用会随供应商配置变化，本轮未记录 Token 或人民币成本，不能与托管 Credits 直接比较。

## 第一轮结论

ZCode 中国版 3.7.6 使用 OpenCode Go API、DeepSeek V4 Flash、最高推理强度和“变更前确认”权限，在 5 分 41 秒内完成 6/6 指定文件，7/7 输入哈希保持一致。过程中发生写入权限确认和人工回复，但没有中断、报错或重试；精确确认/回复次数未记录。

产物结构和材料边界处理较好，目前没有发现访问 `input` 之外文件的证据。目录主动声明是重建提案，写作计划和待办的结构也较完整。主要内容缺陷是自检漏列第 7 个输入要求文件，并没有体现真实的权限确认过程。

本轮不是托管 Auto 模式，而是明确的 BYOK/固定模型组合测试。其速度、质量和成本必须同时归因于 ZCode 的 Agent 工程、OpenCode Go 渠道、DeepSeek V4 Flash、最高推理强度和权限设置。生成的第 0–11 部分目录不能覆盖正式 23 章框架；产品内预览、diff 与 Git/恢复入口留待统一截图核对。
